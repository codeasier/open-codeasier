# Cross Review

## Setup Mode

Treat a first argument of `init` or `setup`, or a natural-language request to set up cross-review, as setup mode rather than a review target. Accept an optional `--local` or `--global` scope and optional local project path; default to local scope and the current directory. Do not call any `cross_review_*` tool in setup mode.

Run `opencode models` before proposing any configuration and treat its output as the authoritative list of connected, exact model identifiers. If it is unavailable or empty, ask the user to provide the available identifiers and do not write a configuration until they do. Do not infer choices from `opencode.json`, hard-code model identifiers, invent placeholders, or limit the user to a predefined provider or model family.

Show the complete discovered list, grouped by provider, before asking the user to choose. Then recommend a reviewer set and an optional judge drawn only from that list. Explain each recommendation briefly: favor strong code reasoning, complementary model families or providers, and distinct review perspectives; avoid selecting aliases of the same underlying model when diverse alternatives exist. Recommend the strongest available evidence-synthesis model for judging, or the parent session when no separate judge is clearly better. Make clear that these are suggestions and that any discovered models may be selected. Mention the token-cost and concurrency tradeoff.

Use the question tool to collect each required field only after presenting the list and recommendations. If the destination already exists at the selected scope, read it first and detect its reviewer format: an existing `reviewers` array, a flat `reviewModels` list, a config without any reviewer key (the model-free `{}` created by `init`, or only non-reviewer keys such as `agents`, `judgeModel`, `maxConcurrency`, or `gitcodeCli`), or an invalid config carrying both keys. If the file is invalid for any other reason — unknown keys, malformed `reviewers` or `reviewModels` values, out-of-range `agents` or `maxConcurrency`, or invalid JSON — stop, show the validation error, and ask the user to repair it before collecting fields. Ask the user to accept or modify the exact reviewer and judge identifiers, then collect max concurrency. Collect an optional reviewer timeout with the question tool: offer a menu of durations (for example 5, 10, 20, 30, 60 minutes) plus a no-preference option, and ask for a custom integer between 5000 and 3600000 milliseconds only if the user chooses one; leave the key out when the user has no preference. After the reviewer fields, ask whether GitCode support is needed. If it is, run `npx open-codeasier detect-gitcode` and do not treat a `gc` binary as gitcode-cli without that check: on macOS `gc` is often Graphviz. A zero exit prints `found: <absolute-path>`; include that path as `gitcodeCli` in the confirmed write. A non-zero exit is not a silent skip: show the install guidance at https://github.com/codeasier/gitcode-cli and ask whether the user wants help installing gitcode-cli, then continue without `gitcodeCli` only if they decline. If GitCode support is not needed, omit `gitcodeCli` for a new destination and preserve an existing `gitcodeCli` when rewriting unless the user asks to remove it. For a new destination, an existing config without a reviewer key, or an existing `reviewers` destination, collect an optional focus for each reviewer; for an existing `reviewModels` destination, collect the flat model list plus one optional shared `focus` instead. The two reviewer formats have different value shapes: `reviewers` is an array of objects, one per reviewer — `[{"model": "provider/model", "focus": "optional focus"}]` with `focus` optional — and is never a flat string array; a flat array of `provider/model` strings is valid only as `reviewModels` — `["provider/model"]`. Use `.opencode/cross-review.json` for local scope and `~/.config/opencode/cross-review.json` for global scope. Do not write until the user confirms the complete selection.

If the destination exists, require explicit confirmation before changing it and preserve its detected `reviewers` or `reviewModels` format; never write `reviewers` alongside an existing `reviewModels` (or vice versa), and on an explicitly confirmed format change replace the old key. When the destination is invalid because it carries both keys, ask the user which of `reviewers` and `reviewModels` to retain, then write that key only, dropping the other while keeping every remaining key such as `agents`, `judgeModel`, `focus`, and `gitcodeCli`. If it does not exist, run `npx open-codeasier init` with the selected scope and optional path after confirmation; this creates an empty, model-free configuration. Write only the user's confirmed exact identifiers and any confirmed optional `reviewerTimeoutMs` and `gitcodeCli`, omit `judgeModel` when the parent session should judge, then validate the written file with `npx open-codeasier validate <written path>`: a non-zero exit is a failed write, so fix the reported validation error and rerun it until it exits 0 — a syntax-only JSON check does not prove the runtime accepts the file — and only then report the path plus the short `/cross-review <target>` invocation.

## Review Mode

Before parsing or reviewing the target, confirm that `cross_review_config`, `cross_review_start`, `cross_review_status`, `cross_review_cancel`, and `cross_review_finalize` are all available in the current session. If any are unavailable, stop immediately; do not use the legacy blocking `cross_review`, substitute task agents, run manual parallel reviews, or use another tool. Look first for a project `.opencode/.open-codeasier/installed-assets.json` that owns `skills/cross-review/SKILL.md`, then for the global `~/.config/opencode/.open-codeasier/installed-assets.json`. Read `packageVersion` from the first matching package-owned manifest and report the exact matching runtime command: `opencode plugin open-codeasier@<packageVersion> --force` for project assets or `opencode plugin open-codeasier@<packageVersion> --global --force` for global assets. Tell the user to restart OpenCode afterward. If neither manifest supplies a valid package version, tell the user to reinstall the runtime plugin and workflow assets at the same exact version and scope. Do not inspect OpenCode's private cache layout.

The tool reads `.opencode/cross-review.json` (project) first and uses it exclusively when present, without reading `~/.config/opencode/cross-review.json` (global); only when the project config is absent does it fall back to the global config. A `reviewers` array assigns each reviewer its own optional `focus`; `reviewModels` values are assigned round-robin across the reviewer count. An optional `reviewerTimeoutMs` (5000-3600000, default 600000) sets the per-session deadline for reviewers and the explicit judge; an explicit `--reviewer-timeout-ms` flag overrides it. An optional `gitcodeCli` absolute path locates gitcode-cli for GitCode targets only. Accept one target plus optional `--review-models`, `--agents`, `--max-concurrency`, `--judge-model`, `--focus`, `--context`, `--evidence-dir`, and `--reviewer-timeout-ms` overrides. Map `--evidence-dir` to `cross_review_start.evidenceDir`, not to a config-preview argument or configuration key. Reject unknown flags, missing values, duplicate flags, or more than one target. `--agents` and `--max-concurrency` accept 1-8; `--reviewer-timeout-ms` accepts 5000-3600000. Use exact OpenCode `provider/model` identifiers from `opencode models`; malformed, disconnected, or unavailable models are errors.

Do not glob `.opencode/**`: OpenCode glob skips hidden directories, so "No files found" is not evidence that project config is absent. The plugin resolves configuration itself sequentially: project `.opencode/cross-review.json` (including the worktree shared-root fallback) first and uses it exclusively when present without reading the global file; only when the project config is absent does it fall back to `~/.config/opencode/cross-review.json`; it does not use `~/.opencode`. Before starting, call `cross_review_config` with only user-supplied overrides, present the resolved config (sources, paths, per-reviewer models with focus, judge, limits, quorum, and any warning), and confirm it with the question tool; re-preview after any config or override change. Call `cross_review_start` with the target plus only user-supplied overrides; never probe config files to reconstruct options, and never copy models from either config file into `--review-models`. Host serialization of omitted optional args as `reviewModels: []` or `0` for `agents` / `maxConcurrency` / `reviewerTimeoutMs` is treated as omitted and uses the loaded config; do not treat that as missing config, and do not copy models into the call to work around it. Reading `gitcodeCli` for a GitCode target is required fetching, not a reviewer-option probe.

Classify the target before `cross_review_start`. A `gitcode.com` URL (`https://gitcode.com/...` or `git@gitcode.com:...`) is GitCode. When the target is not itself a host URL, the repository is GitCode if `git remote -v` includes a `gitcode.com` host. A `github.com` URL is GitHub even if `gitcodeCli` is configured. GitHub and other non-GitCode targets keep using `gh`; a configured `gitcodeCli` must not change GitHub fetching. A GitHub or GitCode pull-request target (a `/pull/<number>` URL, `#<number>`, `PR#<number>`, or `PR <number>` when the repository remote matches the forge) is handled by the plugin itself: it materializes an isolated snapshot worktree at the PR head before any reviewer session exists, so the parent passes the target plus optional notes and evidence attachments, never a fetched PR diff. For a GitCode PR the plugin invokes the configured `gitcodeCli` directly; if it is missing or unusable, the run fails with setup guidance (run `/cross-review setup` or install from https://github.com/codeasier/gitcode-cli) and the parent must not fall back to `gh` or fetch the PR itself. For a GitCode issue target (not a PR), the parent session must still fetch the issue details itself: read `gitcodeCli` from the effective config the plugin resolves - project `.opencode/cross-review.json` exclusively when present, otherwise `~/.config/opencode/cross-review.json` (read those exact files, do not glob) - and invoke that absolute path with `issue view` (number or URL), then pass the result as `context` or stage it in an evidence pack.

Target evidence is gathered once and shared instead of being fetched by every reviewer. For a classified GitHub or GitCode pull request, the plugin materializes an isolated snapshot at the PR head and reports the gatherer as `kind: "adapter"` (no model, session, or reviewer concurrency slot). The worktree plus `.cross-review/meta.json`, `diff.patch`, and `pr.md` are the shared evidence. `notes.md` exists only when caller notes were supplied; `materials/` exists only when a parent pack was attached. Reviewer and judge prompts list only the files present for that run; do not read paths the brief omitted. PR `context` becomes `notes.md`, not embedded prompt text. Do not fetch the PR diff into `context`. An optional parent evidence pack is copied under `.cross-review/materials/`; its metadata and attachments never replace the authoritative adapter metadata or complete `diff.patch`. Adapter or contract failures stop the run before reviewer sessions exist; adapter errors include the retained snapshot path when available.

For `--evidence-dir`, the parent stages a directory before start containing a nonblank `summary.md` and a `meta.json` that parses as a nonempty JSON object, plus any supporting files. Pass a nonblank project-relative subdirectory within the canonical project directory; absolute paths, the project root (`.`), escapes, `.git` entries, symlinks, and non-file/non-directory entries are rejected. The plugin validates and captures the pack bytes, then copies them into the isolated snapshot before creating or dispatching children. Later edits to the source pack do not change the review evidence.

For non-PR targets, supply parent-gathered `context` or an evidence pack. Either skips the LLM gatherer and requires a git repository so the plugin can create a detached snapshot at the range's right-hand commit, or `HEAD` for other targets. A start outside a repository fails with a dedicated error before any child session exists; there is no embedded-context fallback. Any target containing `..` is reserved for a git revision range (`base..head` or `base...head`); other strings that contain `..` are rejected rather than silently pinning `HEAD`. The pack becomes `.cross-review/`; `context` alone creates `meta.json` and `summary.md`, and `context` supplied with a pack is appended to its copied `summary.md`. This evidence is read from files, not embedded in reviewer or judge prompts. Uncommitted changes are not copied from the parent checkout: include the exact diff and any required file contents in the staged pack. Every reviewer and explicit judge is bound to the snapshot directory and must treat only that snapshot as evidence.

Only a non-PR start with neither `context` nor `evidenceDir` uses the configured `judgeModel` for read-only gathering, embedding the gathered output into reviewer briefs. If gathering fails or the user aborts it after timeout, the run degrades to independent fetching. Without `judgeModel`, that start is rejected before any reviewer session is created; the parent must gather evidence first. For PR targets, the parent must not fetch the PR diff into `context`; the adapter owns that evidence.

Normalize the target and focus once. Every reviewer must receive that exact brief (plus the shared context), run read-only, and remain isolated from every other reviewer's output. Call `cross_review_start` once with the normalized arguments and retain its `runID`. The start result includes a `config` resolution block (`sources` plus resolved paths) and a `warning` when the project config was missing; use those fields instead of guessing whether the project file loaded. Poll with `cross_review_status`, which waits on the server side for reviewer progress or up to `waitMs` (default 30s) before returning, eliminating client-side busy-waiting; each call reconciles child sessions, detects reviewer deadlines, and fills available concurrency slots. Never insert a client-side `sleep` between status calls. An overdue session enters `timeout_pending` without being aborted or releasing its concurrency slot, and status returns `actionRequired`. Never resolve it automatically, and never pre-send `timeoutAction` on ordinary polls: ask the user whether to preserve the session or abort it, then call `cross_review_status` once with `timeoutAction: "preserve"` or `timeoutAction: "abort"`. A stray `timeoutAction` while nothing is pending is ignored with a warning. Preserving keeps the same session running, extends its deadline by one configured timeout period, and allows its eventual output into quorum; aborting retains the previous terminal `timed_out` behavior. The default status result is compact (counts plus a per-reviewer `summary`) and omits the config block; request `detail` or `includeOutputs` only when full fields are needed, since `finalize` returns the complete candidates anyway. Call `cross_review_finalize` only when `readyToFinalize` is true (reviewers are terminal, the explicit judge is terminal, or the run is already in a terminal phase). The tool rejects finalize while gathering, reviewers, or the judge are still active, and while a timeout decision is pending. If it starts an explicit judge, poll status until `readyToFinalize` is true again and finalize once more. Use `cross_review_cancel` for cancellation. Do not call the legacy blocking `cross_review` tool.

If `cross_review_start` reports that no review models are configured and no `--review-models` override was given, ask the user which models to use, configure reviewers in `.opencode/cross-review.json` or pass `--review-models`, and call the tool again. The same fallback applies when the preview step reports it.

Require a majority quorum. Preserve each reviewer's model, status, and session provenance. Isolate individual failures; never replace an invalid or failed model silently. On cancellation, stop outstanding work and do not report a partial review as complete.

Treat each finite `status` or `finalize` result as visible progress. A `status` result is compact by default: `counts`, a readable per-reviewer `summary` with the status of the gatherer, every reviewer, and the judge, and the next `pollAfterMs`. Use the `summary` to report each one's own progress rather than only aggregate counts, and do not copy the result payload into the conversation. Continue polling while the gatherer, reviewers, or an explicit judge are active. `cross_review_status` waits on the server side (up to 30s by default) for session progress or state changes before returning, so call `cross_review_status` directly without separate client-side sleeps. When status or finalize returns `actionRequired` for one or more `timeout_pending` sessions, stop polling and use the question tool to ask the user to choose `preserve` or `abort`; explain that preserve keeps the same sessions running and extends their deadlines by one configured timeout period, while abort stops them and excludes them from quorum. A later `abort` also stops a previously preserved session still running inside its extension. Do not choose on the user's behalf. Apply the answer by calling `cross_review_status` once with the returned `runID` and `timeoutAction: "preserve"` or `timeoutAction: "abort"` — the decision also covers timeouts that arise during that call's `waitMs` window — then resume normal polling. Request the full per-reviewer fields only when you actually need them (`detail: true` for field-level state, `includeOutputs: true` to also read review text); `finalize` returns the complete candidates anyway. Call `finalize` only when `readyToFinalize` is true (reviewers are terminal, the explicit judge is terminal, or the run is already in a terminal phase); do not use finalize as a poll — the tool rejects that while gathering, reviewers, or the judge are still active, and while a timeout decision is pending. When it starts an explicit judge, resume status polling and call `finalize` again after `readyToFinalize` is true. If the parent request is cancelled after a run starts, call `cross_review_cancel` with its `runID` when execution resumes. Never start a second run to replace a slow reviewer.

When `--judge-model` or a configured judge model is omitted, use the parent session to judge. Otherwise launch a read-only OpenCode judge session with that explicit model. Independently verify each candidate against the target, reject unsupported claims, deduplicate overlapping findings, and calibrate severity by impact and likelihood. Do not decide by reviewer vote alone. Parent-session finalize returns `pending-parent-consolidation` and retains the snapshot for verification until explicit `cross_review_cancel` or the 7-day expired-run cleanup. A successful explicit-judge finalize removes the snapshot; failed runs retain it until cancel or expired-run cleanup. Do not cancel merely to clean up before parent verification is complete. After parent-session judging is complete — not at finalize — use the question tool to offer clean up versus keep for a retained snapshot; do not offer reuse. Clean up means `cross_review_cancel` on the finished run. Keep leaves the snapshot until a later cancel or the 7-day expired-run cleanup. Expired-run cleanup is best-effort: any manifest whose `updatedAt` is older than 7 days, including abandoned non-terminal runs, is removed with its snapshot worktree on plugin load, finalize, cancel, and when a new run is created.

Report verified findings first in severity order with file and line references. Follow with reviewer provenance, failed or cancelled reviewers, assumptions, and residual testing gaps. State explicitly when no findings survive verification. Mention that parallel reviews increase token usage and cost.
