# Cross Review

## Setup Mode

Treat a first argument of `init` or `setup`, or a natural-language request to set up cross-review, as setup mode rather than a review target. Accept an optional `--local` or `--global` scope and optional local project path; default to local scope and the current directory. Do not call any `cross_review_*` tool in setup mode.

Run `opencode models` before proposing any configuration and treat its output as the authoritative list of connected, exact model identifiers. If it is unavailable or empty, ask the user to provide the available identifiers and do not write a configuration until they do. Do not infer choices from `opencode.json`, hard-code model identifiers, invent placeholders, or limit the user to a predefined provider or model family.

Show the complete discovered list, grouped by provider, before asking the user to choose. Then recommend a reviewer set and an optional judge drawn only from that list. Explain each recommendation briefly: favor strong code reasoning, complementary model families or providers, and distinct review perspectives; avoid selecting aliases of the same underlying model when diverse alternatives exist. Recommend the strongest available evidence-synthesis model for judging, or the parent session when no separate judge is clearly better. Make clear that these are suggestions and that any discovered models may be selected. Mention the token-cost and concurrency tradeoff.

Use the question tool to collect each required field only after presenting the list and recommendations. If the destination already exists at the selected scope, read it first and detect its reviewer format: an existing `reviewers` array, a flat `reviewModels` list, a config without any reviewer key (the model-free `{}` created by `init`, or only non-reviewer keys such as `agents`, `judgeModel`, or `maxConcurrency`), or an invalid config carrying both keys. If the file is invalid for any other reason — unknown keys, malformed `reviewers` or `reviewModels` values, out-of-range `agents` or `maxConcurrency`, or invalid JSON — stop, show the validation error, and ask the user to repair it before collecting fields. Ask the user to accept or modify the exact reviewer and judge identifiers, then collect max concurrency. Collect an optional reviewer timeout with the question tool: offer a menu of durations (for example 5, 10, 20, 30, 60 minutes) plus a no-preference option, and ask for a custom integer between 5000 and 3600000 milliseconds only if the user chooses one; leave the key out when the user has no preference. For a new destination, an existing config without a reviewer key, or an existing `reviewers` destination, collect an optional focus for each reviewer; for an existing `reviewModels` destination, collect the flat model list plus one optional shared `focus` instead. The two reviewer formats have different value shapes: `reviewers` is an array of objects, one per reviewer — `[{"model": "provider/model", "focus": "optional focus"}]` with `focus` optional — and is never a flat string array; a flat array of `provider/model` strings is valid only as `reviewModels` — `["provider/model"]`. Use `.opencode/cross-review.json` for local scope and `~/.config/opencode/cross-review.json` for global scope. Do not write until the user confirms the complete selection.

If the destination exists, require explicit confirmation before changing it and preserve its detected `reviewers` or `reviewModels` format; never write `reviewers` alongside an existing `reviewModels` (or vice versa), and on an explicitly confirmed format change replace the old key. When the destination is invalid because it carries both keys, ask the user which of `reviewers` and `reviewModels` to retain, then write that key only, dropping the other while keeping every remaining key such as `agents`, `judgeModel`, and `focus`. If it does not exist, run `npx open-codeasier init` with the selected scope and optional path after confirmation; this creates an empty, model-free configuration. Write only the user's confirmed exact identifiers and any confirmed optional `reviewerTimeoutMs`, omit `judgeModel` when the parent session should judge, then validate the written file with `npx open-codeasier validate <written path>`: a non-zero exit is a failed write, so fix the reported validation error and rerun it until it exits 0 — a syntax-only JSON check does not prove the runtime accepts the file — and only then report the path plus the short `/cross-review <target>` invocation.

## Review Mode

Before parsing or reviewing the target, confirm that `cross_review_config`, `cross_review_start`, `cross_review_status`, `cross_review_cancel`, and `cross_review_finalize` are all available in the current session. If any are unavailable, stop immediately; do not use the legacy blocking `cross_review`, substitute task agents, run manual parallel reviews, or use another tool. Look first for a project `.opencode/.open-codeasier/installed-assets.json` that owns `skills/cross-review/SKILL.md`, then for the global `~/.config/opencode/.open-codeasier/installed-assets.json`. Read `packageVersion` from the first matching package-owned manifest and report the exact matching runtime command: `opencode plugin open-codeasier@<packageVersion> --force` for project assets or `opencode plugin open-codeasier@<packageVersion> --global --force` for global assets. Tell the user to restart OpenCode afterward. If neither manifest supplies a valid package version, tell the user to reinstall the runtime plugin and workflow assets at the same exact version and scope. Do not inspect OpenCode's private cache layout.

The tool reads configuration from `.opencode/cross-review.json` (project) and then `~/.config/opencode/cross-review.json` (global); project keys override global. A `reviewers` array assigns each reviewer its own optional `focus`; `reviewModels` values are assigned round-robin across the reviewer count. An optional `reviewerTimeoutMs` (5000-3600000, default 600000) sets the per-session deadline for reviewers and the explicit judge; an explicit `--reviewer-timeout-ms` flag overrides it. Accept one target plus optional `--review-models`, `--agents`, `--max-concurrency`, `--judge-model`, `--focus`, `--context`, and `--reviewer-timeout-ms` overrides. Reject unknown flags, missing values, duplicate flags, or more than one target. `--agents` and `--max-concurrency` accept 1-8; `--reviewer-timeout-ms` accepts 5000-3600000. Use exact OpenCode `provider/model` identifiers from `opencode models`; malformed, disconnected, or unavailable models are errors.

Do not glob `.opencode/**`: OpenCode glob skips hidden directories, so "No files found" is not evidence that project config is absent. The plugin resolves configuration itself: project `.opencode/cross-review.json` (including the worktree shared-root fallback) then `~/.config/opencode/cross-review.json`; it does not use `~/.opencode`. Before starting, call `cross_review_config` with only user-supplied overrides, present the resolved config (sources, paths, per-reviewer models with focus, judge, limits, quorum, and any warning), and confirm it with the question tool; re-preview after any config or override change. Call `cross_review_start` with the target plus only user-supplied overrides; never probe config files to reconstruct options, and never copy models from either config file into `--review-models`.

Target context is gathered once and shared instead of being fetched by every reviewer. When an explicit `judgeModel` is configured and no `context` is supplied, the plugin runs a read-only gathering phase in the judge session first (reported as a `gatherer` in status) and embeds the gathered output into every reviewer brief; if gathering fails, or reaches its timeout and the user chooses to abort it, the run degrades to independent fetching, and the judge later verifies from its own gathered history. When no `judgeModel` is configured, the parent session will judge, and the plugin cannot gather for you: collect the target context (the exact diff, issue body, or change summary) in the parent session before calling `cross_review_start` and pass it as `context` so reviewers do not each fetch it. A `context` argument always skips the gathering phase and is embedded in every reviewer brief and in the judge prompt.

Normalize the target and focus once. Every reviewer must receive that exact brief (plus the shared context), run read-only, and remain isolated from every other reviewer's output. Call `cross_review_start` once with the normalized arguments and retain its `runID`. The start result includes a `config` resolution block (`sources` plus resolved paths) and a `warning` when the project config was missing; use those fields instead of guessing whether the project file loaded. Poll with `cross_review_status`, which waits on the server side for reviewer progress or up to `waitMs` (default 30s) before returning, eliminating client-side busy-waiting; each call reconciles child sessions, detects reviewer deadlines, and fills available concurrency slots. An overdue session enters `timeout_pending` without being aborted or releasing its concurrency slot, and status returns `actionRequired`. Never resolve it automatically: ask the user whether to preserve the session or abort it, then call `cross_review_status` once with `timeoutAction: "preserve"` or `timeoutAction: "abort"`. Preserving keeps the same session running, extends its deadline by one configured timeout period, and allows its eventual output into quorum; aborting retains the previous terminal `timed_out` behavior. The default status result is compact (counts plus a per-reviewer `summary`) and omits the config block; request `detail` or `includeOutputs` only when full fields are needed, since `finalize` returns the complete candidates anyway. Call `cross_review_finalize` after reviewers become terminal. If it starts an explicit judge, poll status until the judge is terminal and finalize again. Use `cross_review_cancel` for cancellation. Do not call the legacy blocking `cross_review` tool.

If `cross_review_start` reports that no review models are configured and no `--review-models` override was given, ask the user which models to use, write a project `.opencode/cross-review.json`, and call the tool again. The same fallback applies when the preview step reports it.

Require a majority quorum. Preserve each reviewer's model, status, and session provenance. Isolate individual failures; never replace an invalid or failed model silently. On cancellation, stop outstanding work and do not report a partial review as complete.

Treat each finite `status` or `finalize` result as visible progress. A `status` result is compact by default: `counts`, a readable per-reviewer `summary` with the status of the gatherer, every reviewer, and the judge, and the next `pollAfterMs`. Use the `summary` to report each one's own progress rather than only aggregate counts, and do not copy the result payload into the conversation. Continue polling while the gatherer, reviewers, or an explicit judge are active. `cross_review_status` waits on the server side (up to 30s by default) for session progress or state changes before returning, so call `cross_review_status` directly without separate client-side sleeps. When status or finalize returns `actionRequired` for one or more `timeout_pending` sessions, stop polling and use the question tool to ask the user to choose `preserve` or `abort`; explain that preserve keeps the same sessions running and extends their deadlines by one configured timeout period, while abort stops them and excludes them from quorum. A later `abort` also stops a previously preserved session still running inside its extension. Do not choose on the user's behalf. Apply the answer by calling `cross_review_status` once with the returned `runID` and `timeoutAction: "preserve"` or `timeoutAction: "abort"` — the decision also covers timeouts that arise during that call's `waitMs` window — then resume normal polling. Request the full per-reviewer fields only when you actually need them (`detail: true` for field-level state, `includeOutputs: true` to also read review text); `finalize` returns the complete candidates anyway. Call `finalize` when reviewers are terminal; when it starts an explicit judge, resume status polling and call `finalize` again after the judge becomes terminal. If the parent request is cancelled after a run starts, call `cross_review_cancel` with its `runID` when execution resumes. Never start a second run to replace a slow reviewer.

When `--judge-model` or a configured judge model is omitted, use the parent session to judge. Otherwise launch a read-only OpenCode judge session with that explicit model. Independently verify each candidate against the target, reject unsupported claims, deduplicate overlapping findings, and calibrate severity by impact and likelihood. Do not decide by reviewer vote alone.

Report verified findings first in severity order with file and line references. Follow with reviewer provenance, failed or cancelled reviewers, assumptions, and residual testing gaps. State explicitly when no findings survive verification. Mention that parallel reviews increase token usage and cost.
